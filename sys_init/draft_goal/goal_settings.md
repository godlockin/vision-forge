# 目标

构建一个外接的agent 专家体系，用来对大模型，特别是生图/生视频模型的结果进行评估、优化和迭代升级。

# 任务与统一接口

1. **标准统一交互接口 (Standard I/O Interface)**
   - **输入 (Input)**：`原始需求 (User Prompt)` + `源媒体文件 (可选图像/视频)` + `目标受众/用途 (Target Context)` + `约束条件 (Constraints)`。
   - **输出 (Output)**：`迭代优化后的最终媒体结果` + `专家评审与洞察报告 (含多维打分)` + `优化过程追溯记录 (日志文件路径)` + `最终被采纳的优化Prompt`。
2. 建立专家优化工作组，包含多名静态与动态成员。
3. 设立统一数据存储与异步持久化机制：任务过程中的所有中间态文件（图像原图、视频片段）、专家组的黑板讨论日志与打分记录等，都将通过**异步 Flush (Asynchronous I/O)** 的方式写入落盘，用于后续合规审查与系统逻辑回溯。

# 核心概念与专家分类

1. **静态专家组**：系统常驻的骨干成员，负责全局把控与特定必要环节。
   - **项目经理 (PM)**：把控任务整体进度、组织沟通流转。在意见死锁时强行打断讨论，并计算加权汇总当前的最佳决议。**自身不参与具体视觉生成或拆解分析的细枝末节。**
   - **合规与法律专家 (Compliance & Legal)**：**不参与任何任务拆解、分配与具体执行过程**。仅在任务启动之初对用户需求进行合规拦截，并在任务交付前对最终产出进行严格安全与法律红线审查。拥有**一票否决权**。
     - **[重绘补救自动回退 (Auto-Fallback)]**：若合规审查未通过，对于**中低严重等级**（如版权IP、名人肖像、品牌商标相似），自动提取违规情况并触发重绘补救机制（如局部重绘 Inpainting、元素替换、风格调整）。对于**极高严重等级**（政治敏感、色情暴力），则直接出具合规阻断报告并拦截。
   - **视觉专家 (Visual Expert)**：核心执行与审核成员。如果不引入其他领域专家，该成员将直接分裂为“分析与执行”实例和“严苛与完美主义审核”实例。
   - **知识管理员 (Knowledge Admin)**：独立运行的辅助实例，负责监控并维护系统的“共享黑板”（即公共记忆），并在其达到长度阈值后执行静默记录、提炼分析与内容压缩。

2. **动态领域专家**：根据任务目标动态引入的特别领域专家（如UI排版专家、3D游戏资产专家等），一旦引入也会根据需要分裂为“执行阵营”和“挑剔审核阵营”。

# 专家基础设定 (Agent Schema)

1. 每位常驻专家与动态专家都具备完整、丰满与极具个性的人物设定。
2. 所有专家配置统一采用 `yml` 文件进行声明。配置模板必须包含以下核心细化维度：
   - **`Role (角色与定位)`**
   - **`Persona & Background (人设与背景)`**
   - **`Personality (性格特征)`**
   - **`Thinking Framework (思维框架与决策方式)`**
   - **`Strengths (核心优势)`**
   - **`Weaknesses (潜在劣势)`**
   - **`Blind Spots (可能的疏忽点)`**：在复杂任务中容易忽略的盲区细节。
   - **`Superhuman Insights (超人的洞察能力点)`**：该角色所具备的远超常人的独特切入点和敏锐度。
   - **`Capabilities & Skills (核心能力树与适用场景)`**
   - **`Confidence Threshold (置信度预设阈值)`**：定义专家承接任务的底线要求。自签置信度过低将触发 PM 或 HR 的重新评估/换人干预。
3. 每位专家除了感知与写入“共享黑板”外，均配有自己独立的短/长期工作记忆空间用来进行反思和打分。

# 优化流转与共识机制 (Workflow)

采用 **黑板模式 (Blackboard Pattern)** 作为核心协作框架。

1. **[一票否决] 需求准入**：用户输入到达后，优先交由合规与法律专家进行审核。若存在底线违规风险，直接否决并驳回。
2. **任务初始化与可行性打分**：项目经理和视觉专家分析目标，决定是否引入其他领域专家。在分配任务并初始化专家实例时，项目组会对该领域专家**“是否有足够能力处理该任务”进行可行性打分 (Feasibility Score)**。
3. **能力置信度自签**：专家接到分配的子任务后，会自动根据自身能力设定一个**置信度 (Confidence Score)**，评估自己能完美承接该任务的把握。
4. **阵营分裂与混合并发**：系统根据任务图谱分裂为负责完成指标的“执行组”和苛刻挑剔的“审核组”。若有上下游链路则严格串行执行；无依赖的节点则分配并拉起多线程进行并发处理。
5. **黑板讨论与加权互评**：所有阶段性产出和意见均直接同步到“共享黑板”中。专家们自由浏览黑板并进行多轮发言。在表达意见或评价他人方案时，他们会给出一个支持评分。**最终采纳这个评分时，将综合“可行性打分”与“置信度”以及历史准确率等动态因子进行加权计算 (Weighted Consensus)**。
   - **[事件驱动追加 (Event Sourcing)]**：专家无权修改历史意见，只能将观点作为流事件 (Event流如 `opinion_added`, `score_submitted`) 追加。系统配置有事件去重窗，且关键事件（如违规）可通过事件订阅总线实时推送通知给相关专家。
6. **[强制打断与干预策略] 投票收敛与死锁处理**：
   - 设定严格的讨论**软性轮数限制**（如5轮触发警告）和**死锁检测**（如连续3轮无进展意见同质化）。触发死锁时，PM 有权通过“拆分争议点”、“替换争议专家”、甚至“直接由PM强制裁决”来收敛讨论推选最优解。
7. **最终审查**：产出的最终结果将通过共享黑板直接提交给合规与法律专家，进行最后一次严格合规把控发布。若遭否决，即视违规等级触发**重绘补救机制 (Auto-Fallback)** 或直接驳回。

# 技术与底层设定

1. **智能模型路由规则 (Model Smart Routing)**：采用动态路由架构调配 Azure OpenAI 与 Google Vertex AI。
   - **允许使用的模型**：
     - Azure OpenAI: GPT-4o 系列、GPT-4o-mini、o1-preview、o1-mini
     - Vertex AI: Gemini 2.5/3.0 Pro/Flash、Imagen-3/Imagen-3-fast
   - **明确禁止的模型**：
     - Azure OpenAI: GPT-4 及更早版本（GPT-4-32k、GPT-4-turbo、GPT-35-turbo）
     - Vertex AI: Gemini 2.5 之前版本（Gemini 1.0、Gemini 1.5 系列）
   - **路由策略**：核心节点和复杂推理优先分配 GPT-4o 或 Gemini-3.0-Pro；生图环节默认调用 Vertex AI 的 Imagen-3；轻量化或摘要压缩节点降级至 GPT-4o-mini / Gemini-2.5-flash，保障质量与成本的最佳平衡。

2. **底层媒体抽象控制**：抽象出底层媒体处理接口，默认通过 Vertex AI 层直接拉起图像处理内核。

3. **流量控制与调度重试队列 (Rate Limiter & Priority Queue)**：
   - 设计全局**令牌桶限流**及**指数退避重试 (Exponential Backoff)** 的网关管控层，针对两家云厂商 API 的差异化 TPM/RPM 配额设置独立限速池。
   - 建立高低优通道调度策略，确保 PM 决策与合规拦截永远享有最高资源优先级，防止出现"堵车死锁"问题。
   - 限流配置详见 `sys_init/settings/rate_limits.yml`，模型路由配置详见 `sys_init/settings/model_routing.yml`。
