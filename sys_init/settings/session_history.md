## 二、设计讨论过程

### 第一轮：项目定位澄清

**用户澄清**：
> 主要是自动评估，我在构建一个通过自然语言和简单的交互操作进行图片操作的 agent 平台，里面会包含一些图像操作，如删除沙发，把灯调亮等等…当前项目就是承接这些需求，根据用户实际提出的需要，配合一些他的输入对任务进行拆分和细化，操作图片，然后对结果进行评估、优化，最终返回

**关键理解**：
- 这是一个**图像操作 Agent 平台**
- 本项目是平台的"评估与优化引擎"
- 输入：基础图片 + 用户期望（自然语言 + 动作关键词）+ 参考信息（mask/boundingbox）
- 输出：满足用户要求的高质量最终结果

### 第二轮：评估对象确认

**用户确认**：
> 全流程负责，平台期望的输入是用户的基础图片（可能多张）+ 用户的期望（自然语言 + 行为/动作关键词）+ 参考信息（如 mask、boundingbox 等），期望的输出是满足用户期望、要求、设定、限制的，高质量的最终结果。

**设计决策**：
- 专家系统**全流程负责**：需求理解→任务拆解→执行调度→结果评估→迭代优化
- 不是单纯的评估工具，而是执行 + 评估的闭环系统

### 第三轮：评估模式确认

**用户确认**：
> 混合模式，专家先进行评估、处理、迭代、优化、输出结果，但是会把整个链路记录下来，如删除物品 A、删除物品 B、添加物品 C…如果用户对最终结果不满意，则展示整个处理链路，让用户进行 fork 并继续处理

**设计决策**：
- **混合评估模式**：规则检查（客观）+ LLM 评估（主观）
- **操作链路可追溯**：记录所有中间操作
- **用户可 fork**：不满意时可回溯到任意节点继续处理

### 第四轮：记忆空间设计

**用户确认**：
> 以上全部，而且动态初始化出来的专家和工具、skills 也会被记录和索引下来

**设计决策**：
- **完整记忆体系**：任务历史 + 评价进化 + 用户偏好 + 领域知识 + 动态专家索引
- **专家注册机制**：新专家被索引到专家库，系统能力持续进化

### 第五轮：动态专家生成机制

**用户确认**：
> 混合模式，预设一些专家按需加载，同时根据任务种类、状态、进度、当前专家能力缺口等动态初始化和加载新的专家（如果需要）。这些专家会根据自己能力、属性、标签组成组织架构索引起来，方便后续调用，让系统能力越来越强越来越全面

**设计决策**：
- **预设 + 动态混合模式**
- **HR 专家主导**：资深 HR 配合领域专家定义新专家
- **能力标签索引**：支持检索和复用

### 第六轮：技术栈确认

**用户确认**：
> 大模型通过云端接口调用，但是系统运行在本地；多专家通过并行框架进行处理，可以通过多线程/多进程混合的方式。限制不要多租户。

**设计决策**：
- **本地运行 + 云端 API**
- **Python 多线程/多进程混合**
- **单用户模式**（无多租户需求）

### 第七轮：专家 YAML 配置

**用户反馈**：
> 可以更丰富一点，参考我更新过的 @sys_init/draft_goal/goal_settings.md，先设置专家模板，然后设置静态专家，动态专家由领域专家、HR 配合大模型一起填充和定义

**设计决策**：
- 基于用户更新的 goal_settings.md 设计完整 Schema
- 包含置信度阈值字段
- 动态专家由 LLM 基于模板填充

### 第八轮：专家角色补充

**用户补充**：
> 复合，还需要包括 prompt engineer，摄影师，图像编辑，室内设计师，陈列设计师等静态专家按需加载；字段目前可以；预设框架，然后按照对领域专家的期待进行填充。

**设计决策**：
- 10 位静态专家：4 位常驻 + 6 位按需加载
- 按需加载专家：HR、Prompt 工程师、摄影师、图像编辑师、室内设计师、陈列设计师

## 三、用户提出的关键工程问题

在基本设计完成后，用户提出了 4 个值得进一步明确的关键点：

### 问题 1：技术底座与并行机制控制

**用户原文**：
> 由于我们使用的是 OpenAI (Azure) 和 Google Vertex AI，高并发发包极易触发 API 的 Rate Limit (尤其是 TPM/RPM 限制)。建议在底层模型请求封装层，需要明确增加一套 Token 桶令牌限流器 (Rate Limiter) 或是 带有 Exponential Backoff (指数退避) 策略的重试队列，防止因为专家并发热烈讨论而导致整体链路崩溃。

**解决方案**：
- 创建 `rate_limits.yml`
- Token 桶限流（Azure 60 RPM/500K TPM, VertexAI 30 RPM/300K TPM）
- 指数退避重试（最多 3 次，backoff 2x，jitter 10%）
- 请求优先级队列（PM/合规高优先级）

### 问题 2：黑板模式的状态锁或冲突处理

**用户原文**：
> 当多个分裂实例（如执行组和审核组）并发地向"黑板"写入见解或打分时，容易产生脏读或覆盖。建议在此架构中明确定义黑板写入的锁机制 (Lock) 或者事件驱动追加模式 (Append-only Event Sourcing)。即专家不能随意修改黑板已有的历史，只能追加新事件记录；再由知识管理员 (Knowledge Admin) 统一进行读取、规整和定期压缩。

**解决方案**：
- 创建 `blackboard_events.yml`
- Append-only Event Sourcing 模式
- 事件去重窗口（5 秒内相同专家相同类型视为重复）
- 知识管理员定期压缩（100 事件或 2 分钟触发）

### 问题 3：YAML 配置中的打分加权关联缺失

**用户原文**：
> 在 static_experts.yml 和 dynamic_expert_template.yml 中，针对"可行性打分"和"置信度"，虽然文档规划了，但 YAML 中没有体现其预设字段或范围上限。建议在专家的 YAML Schema 的 decision_style 或 i_o_spec 里增加默认下限限制。比如：如果一个动态专家自签名的置信度低于 0.5（满分 1.0），则强行触发 PM 的干预或让 HR 重新物色新专家。

**解决方案**：
- 创建 `intervention_rules.yml`
- 置信度阈值：0.5 通知 PM，0.3 自动重新分配
- 可行性打分：<7 分复审，<5 分专家组复审
- 加权计算：可行性 40% + 置信度 30% + 互评 30%

### 问题 4：极端场景的回退方案

**用户原文**：
> 如果在最后环节，"合规与法律专家"行使了一票否决权（比如发现生成图像中出现了受版权保护的 IP），原设计是"直接否决并驳回"。建议是直接把 error 抛给用户结束任务，还是自动提取违规的关键词（如"移除了含有皮卡丘的元素"），并自动触发一轮无需人工介入的 "重绘补救机制 (Auto-Fallback)"？这在实际工程落地中直接影响使用体验。

**解决方案**：
- 创建 `fallback_policy.yml`
- 违规分类：高严重等级（直接驳回）vs 中低严重等级（Auto-Fallback）
- Auto-Fallback 策略：inpainting → element_replacement → style_divergence
- 最多 3 次尝试，失败后附详细报告驳回

### 问题 5：模型智能路由（用户补充）

**用户补充**：
> 除此之外还要增加模型智能路由，根据不同层次/需求动态选择不同种类的模型，如 gemini-3.1/3.0 pro/flash 等，但是要禁止使用 gpt-4 和 gemini-2.5 以前的版本

**解决方案**：
- 创建 `model_routing.yml`
- 模型白名单机制
- 允许：GPT-4o 系列、Gemini 2.5/3.0 Pro/Flash、Imagen-3
- 禁止：GPT-4 及更早版本、Gemini 2.5 之前版本
- 任务类型路由：text_reasoning、vision_analysis、image_generation 等

## 五、核心设计理解

### 项目本质

**Intelligent Vision Reviewer** 不是一个简单的评估工具，而是一个**全流程负责的图像操作 Agent 专家系统**。它接收用户的模糊意图（自然语言 + 参考信息），通过多专家协作完成：
1. 需求理解与合规审查
2. 任务拆解与专家分配
3. 并行执行与相互评审
4. 迭代优化与质量把控
5. 最终交付与链路追溯

### 关键设计哲学

1. **制衡机制**：执行组 vs 审核组的分裂设计，形成内部质量把控
2. **可追溯性**：所有操作记录为可 fork 的链路，用户可回溯到任意节点
3. **渐进进化**：动态专家被索引到专家库，系统能力持续增强
4. **防御性设计**：置信度阈值、死锁检测、Auto-Fallback 等多层保护
5. **成本意识**：模型智能路由，在保证质量前提下优先选择性价比高的模型

### 技术架构特点

```
┌─────────────────────────────────────────────────────────────┐
│                      专家应用层                              │
│  (10 位静态专家 + 动态专家，多实例并发执行)                    │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                      请求调度层                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
│  │ 模型智能路由  │  │ Token 桶限流  │  │ 指数退避重试  │       │
│  └──────────────┘  └──────────────┘  └──────────────┘       │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                      模型适配层                              │
│      Azure OpenAI SDK          │      Vertex AI SDK         │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                      云端模型层                              │
│  GPT-4o / Gemini Pro  │  Imagen-3 / 嵌入模型                 │
└─────────────────────────────────────────────────────────────┘
```

### 核心创新点

1. **可行性打分 + 置信度自签**：任务分配时评估专家能力，专家接单后自评置信度，两者加权计入最终决策
2. **Append-only 黑板**：专家只能追加事件不能修改历史，知识管理员定期压缩摘要
3. **Auto-Fallback**：合规违规自动尝试修复（最多 3 次），失败后附详细报告驳回
4. **动态专家注册**：新专家根据任务需求动态生成并索引到专家库
