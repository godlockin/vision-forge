## 一、系统目标

构建一个全流程负责的图像操作 Agent 专家系统，用于对大模型（特别是生图/生视频模型）的生成结果进行评估、优化和迭代升级。

### 1.1 标准输入输出接口

**输入 (Input)**：
- 原始需求 (User Prompt)
- 源媒体文件（图像/视频，可多张）
- 目标受众/用途 (Target Context)
- 约束条件（mask、boundingbox 等参考信息）

**输出 (Output)**：
- 迭代优化后的最终媒体结果
- 专家评审与洞察报告（含多维打分）
- 优化过程追溯记录（操作链路日志）
- 最终被采纳的优化 Prompt

### 1.2 数据存储机制

任务过程中的所有中间态文件（原图、视频片段）、专家组讨论日志、打分记录等，通过**异步 Flush (Asynchronous I/O)** 方式写入落盘，用于后续合规审查与系统逻辑回溯。

## 二、专家分类与职责

### 2.1 静态专家组（Static Experts）

系统常驻骨干成员，配置在 `experts/static/` 目录下。

| 专家角色 | 职责 | 加载策略 |
|---------|------|---------|
| **项目经理 (PM)** | 任务拆解、进度把控、死锁打断、加权投票 | 始终加载 |
| **合规与法律专家** | 需求准入审核 + 最终产出审查，拥有一票否决权 | 始终加载 |
| **视觉专家** | 核心执行与审核，可分裂为执行/审核实例 | 始终加载 |
| **知识管理员** | 共享黑板管理、记忆压缩与索引 | 始终加载 |
| **资深 HR 专家** | 能力缺口识别、动态专家"招聘"与评估 | 按需加载 |
| **Prompt 工程师** | 模糊需求转化、跨模型 prompt 适配 | 按需加载 |
| **摄影师** | 光线/构图分析、真实感评估 | 按需加载 |
| **图像编辑师** | 复杂编辑拆解、mask 生成、精修 | 按需加载 |
| **室内设计师** | 空间布局、风格搭配、家具规划 | 按需加载 |
| **陈列设计师** | 商品展示、视觉营销、品牌调性把控 | 按需加载 |

### 2.2 动态专家组（Dynamic Experts）

根据任务需求动态生成，配置在 `experts/dynamic/` 目录下。

**生成机制**：
- 由资深 HR 专家主导，领域相关静态专家配合
- 基于预设模板，通过 LLM 根据领域描述填充完整配置
- 生成后进行可行性打分，通过后注册到专家库

**生命周期**：
- 任务创建 → 实例化（执行/审核分裂）→ 任务执行 → 归档到记忆

## 四、工作流转与共识机制

采用**黑板模式 (Blackboard Pattern)** 作为核心协作框架。

```
┌─────────────────────────────────────────────────────────────────┐
│                        用户请求入口                              │
│              (图片 + 自然语言 + 动作关键词+参考信息)                │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    [一票否决] 合规与法律审核                       │
│                   审核通过？是 → 继续 | 否 → 驳回                  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    任务初始化与可行性分析                          │
│         PM+ 视觉专家+HR 分析目标 → 决定引入哪些领域专家              │
│              对每位专家进行「可行性打分」(Feasibility Score)       │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    专家能力置信度自签                            │
│           专家接到任务后设定「置信度」(Confidence Score)          │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    阵营分裂与混合并发                            │
│    ┌─────────────────┐       ┌─────────────────┐                │
│    │   执行组 (Executor)  │       │   审核组 (Critic)   │                │
│    │  负责完成指标     │       │  刻薄挑剔完美主义 │                │
│    └─────────────────┘       └─────────────────┘                │
│    依赖关系→串行执行 | 无依赖→多线程并行                           │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    黑板讨论与加权互评                            │
│  - 所有产出和意见同步到「共享黑板」                               │
│  - 专家自由浏览并发言，给出支持评分                              │
│  - 最终采纳 = 评分 × (可行性打分 × 置信度) 的加权计算              │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│              [强制打断] 投票收敛算法（如讨论超阈值）                │
│           PM 打断无意义辩论 → 启动加权投票 → 强制选出最优解         │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    [一票否决] 最终合规审查                        │
│                   合规专家对产出进行最后把关                       │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    结果交付与链路记录                            │
│  - 最终媒体结果                                                  │
│  - 专家评审报告（多维打分）                                      │
│  - 操作链路日志（删除 A、添加 B、调整 C...）                      │
│  - 支持用户 fork 并继续处理                                       │
└─────────────────────────────────────────────────────────────────┘
```

## 五、记忆空间设计

### 5.1 记忆层次

| 层次 | 范围 | 内容 | 保留策略 |
|-----|------|------|---------|
| **任务记忆** | 单任务内 | 当前任务的中间状态、临时决策 | 任务结束清除 |
| **会话记忆** | 单 session | 当前会话的专家交互记录 | Session 结束清除 |
| **持久记忆** | 全局共享 | 任务历史、用户偏好、领域知识 | 压缩后永久保存 |

### 5.2 共享黑板（Shared Blackboard）

所有专家可感知和写入的公共记忆空间，由知识管理员负责：
- 监控内容增长
- 达到阈值后触发压缩
- 关键信息提取与摘要
- 语义索引与检索

### 5.3 专家索引库

动态专家和工具注册到索引库，包含：
- 能力标签
- 领域标签
- 历史表现记录
- 适用场景

## 六、技术架构

### 6.1 整体架构分层

```
┌─────────────────────────────────────────────────────────────────┐
│                        专家应用层                                │
│    (PM / 视觉专家 / 合规专家 / HR / ... 10 位静态专家)             │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                      请求调度层                                  │
│   ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐ │
│   │  模型智能路由    │  │  Token 桶限流    │  │  指数退避重试   │ │
│   │  Model Router   │  │  Rate Limiter   │  │  Retry Queue    │ │
│   └─────────────────┘  └─────────────────┘  └─────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                      模型适配层                                  │
│   ┌─────────────────┐              ┌─────────────────┐          │
│   │  Azure OpenAI   │              │  Vertex AI SDK  │          │
│   │  SDK            │              │  (Gemini)       │          │
│   └─────────────────┘              └─────────────────┘          │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                      云端模型层                                  │
│   GPT-4o / GPT-4o-mini     │     Gemini 2.5/3.0 Pro/Flash       │
│   o1-preview / o1-mini     │     Imagen-3 / Imagen-3-fast       │
└─────────────────────────────────────────────────────────────────┘
```

### 6.2 大模型层

**支持的模型供应商与模型：**

| 供应商 | 文本推理 | 视觉分析 | 图像生成 | 嵌入模型 |
|-------|---------|---------|---------|---------|
| **Azure OpenAI** | GPT-4o, GPT-4o-mini, o1-preview, o1-mini | GPT-4o (多模态) | - | text-embedding-3-small/large |
| **Vertex AI** | Gemini 2.5-Pro/Flash, Gemini 3.0-Pro/Flash | Gemini 全系列 | Imagen-3, Imagen-3-fast | text-embedding-005 |

**明确禁止的模型：**
- Azure OpenAI: GPT-4 及更早版本 (GPT-4-32k, GPT-4-turbo, GPT-35-turbo 等)
- Vertex AI: Gemini 2.5 之前版本 (Gemini 1.0, Gemini 1.5 系列)

详见 `model_routing.yml` 中的模型白名单配置。

### 6.3 请求调度层

**Token 桶限流器 (Rate Limiter)：**

```yaml
# 配置于 rate_limits.yml
azure_openai:
  rpm_limit: 60           # 每分钟请求数
  tpm_limit: 500000       # 每分钟 token 数
  burst_size: 10          # 令牌桶容量

vertex_ai:
  rpm_limit: 30
  tpm_limit: 300000
  image_gen_rpm_limit: 10 # 生图 API 更严格
```

**指数退避重试 (Exponential Backoff Retry)：**

```yaml
retry:
  max_attempts: 3
  backoff_multiplier: 2.0     # 指数退避倍数
  initial_delay_ms: 1000      # 初始延迟 1 秒
  max_delay_ms: 30000         # 最大延迟 30 秒
  jitter: 0.1                 # 随机抖动 10%
```

**请求优先级：**
- **High**: 合规审查、PM 决策
- **Normal**: 视觉专家、Prompt 工程师、摄影师
- **Low**: 室内设计师、陈列设计师、知识管理员

### 6.4 并发控制

**并发限制配置：**

```yaml
concurrency:
  max_concurrent_requests: 10       # 全局最大并发
  max_concurrent_per_provider: 5    # 每供应商最大并发
  max_concurrent_per_expert: 2      # 每专家实例最大并发
```

**死锁处理：**
- 连续 3 轮无进展 → 死锁检测触发
- PM 介入 → 拆分投票/替换专家/直接决策

详见 `rate_limits.yml` 完整配置。

---

### 6.5 共享黑板 (Blackboard) 并发控制

**写入模式：Append-only Event Sourcing**

所有专家只能向黑板追加新事件，不能修改历史：

```yaml
# 配置于 blackboard_events.yml
concurrency_control:
  write_mode: "append_only"
  round_based:
    enabled: true
    default_round_time_ms: 30000
    max_rounds: 10
  deduplication:
    enabled: true
    window_ms: 5000
```

**事件类型：**
- `opinion_added` - 专家发表意见
- `score_submitted` - 专家打分
- `decision_made` - 阶段性决策
- `round_closed` - PM 关闭一轮讨论
- `veto_triggered` - 合规专家一票否决
- `snapshot_compressed` - 知识管理员压缩摘要

**知识管理员职责：**
- 监控事件增长（阈值：100 事件 或 2 分钟）
- 定期压缩摘要（压缩率约 30%）
- 语义索引与归档

详见 `blackboard_events.yml` 完整配置。

### 6.6 媒体处理抽象

默认通过 Vertex AI 层调用 Gemini 原生模型作为图像处理内核，抽象出统一接口支持多供应商。

**图像操作类型：**
- Inpainting (局部重绘)
- Outpainting (扩展绘制)
- Style Transfer (风格转换)
- Element Replacement (元素替换)
- Quality Enhancement (质量增强)

### 6.8 降级与回退策略

**API 降级：**
- Azure 限流 → 等待重试 → 切换到 Vertex AI
- Vertex AI 超时 → 队列等待 → 通知 PM

**合规违规 Auto-Fallback：**

| 违规类型 | 严重等级 | 处理方式 |
|---------|---------|---------|
| 敏感内容 | 高 | 直接驳回 |
| 版权/IP | 中 | Auto-Fallback (最多 3 次) |
| 品牌/商标 | 中 | Auto-Fallback (最多 2 次) |
| 名人肖像 | 中 | Auto-Fallback (最多 2 次) |
| 质量不达标 | 低 | Auto-Fallback (最多 2 次) |

详见 `fallback_policy.yml` 完整配置。

## 七、专家干预与阈值控制

### 7.1 置信度阈值

| 阈值 | 触发动作 |
|-----|---------|
| 置信度 < 0.5 | 通知 PM，建议重新分配 |
| 置信度 < 0.3 | 自动触发 HR 重新招聘专家 |
| 置信度 > 0.8 | 加权系数 +15% |

### 7.2 可行性打分

| 打分范围 | 动作 |
|---------|------|
| < 5 分 | 专家组复审（PM+ 视觉专家+HR） |
| 5-7 分 | PM 决策是否继续 |
| >= 7 分 | 通过 |
| >= 8.5 分 | 快速通道，减少监督 |

### 7.3 讨论轮数控制

| 轮数 | 动作 |
|-----|------|
| 3 轮 | PM 关注进度 |
| 5 轮 | PM 警告提醒 |
| 8 轮 | PM 建议干预 |
| 10 轮 | 强制投票 |
| 15 轮 | 紧急决议（PM 直接决策） |

### 7.4 加权共识计算

```yaml
weights:
  feasibility: 0.4      # 可行性打分权重 40%
  confidence: 0.3       # 置信度权重 30%
  peer_score: 0.3       # 互评评分权重 30%
```

详见 `intervention_rules.yml` 完整配置。

## 八、关键设计决策

1. **一票否决权**：合规与法律专家在需求准入和最终交付两个节点拥有不可覆盖的否决权
2. **可行性打分 + 置信度自签**：任务分配时评估专家能力，专家接单后自评置信度，两者加权计入最终决策
3. **执行/审核分裂**：无其他领域专家时，视觉专家分裂为执行和审核两个 instance；有多领域专家时，分裂为两个阵营
4. **操作链路可追溯**：所有中间操作（删除 A、调亮 B、添加 C...）记录为可 fork 的链路
5. **动态专家注册**：新专家被索引到专家库，系统能力持续进化
6. **API 限流与重试**：Token 桶限流 + 指数退避重试，防止并发请求压垮 API
7. **黑板 Append-only**：专家只能追加事件，不能修改历史，由知识管理员定期压缩
8. **模型智能路由**：根据任务类型动态选择最合适模型，禁止使用 GPT-4 和 Gemini 2.5 之前版本
9. **Auto-Fallback**：合规违规可修复时自动尝试补救（最多 3 次），失败后驳回并附详细报告
